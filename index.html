Where we stand

Contributing to a robotics sim
is a wall.

01

Technical surface

Modern C++, CMake, ROS, Gazebo plugins, SDF/URDF, Xdyn. Every brick has its idioms. The learning curve is real.

02

Physical coupling

A sensor isn't just a class: it's a physical model, a ROS message, a Gazebo plugin, and a launch scenario integration.

03

Implicit conventions

Topic naming, plugin structure, C++ style, launchfile format. All the things never written in the README.

Many good ideas die between « I want to contribute » and « my PR is ready ».

Why now

AI agents crossed the useful threshold.

Not for demos. For production code.

Three things shifted late 2025:

  • Models good at tool calling. Opus 4.5, GPT-5.2: multi-step tool chains stay on track.
  • Long context windows. A whole codebase + docs + conventions in one shot, no lossy summaries.
  • Sustained autonomy. Not a bigger prompt: the agentic loop, map → build → run → test → review, until green.
# what wasn't true 18 months ago
$ claude "explain the Gazebo plugin → ROS topic pipeline in systems/"
→ answer in 30 s, with file:line pointers

$ claude "propose 2 ways to add an RC sailboat to LOTUSim"
→ two strategies, explicit trade-offs

$ claude "implement option B + tests + doc"
→ readable first draft, ready to challenge

An agent can write code. So: how do we handle agent-assisted contributions, responsibly?

Two communities already answered.

Industry signal · the question got answered

The Linux kernel the most conservative community

A policy written for the agents: coding-assistants.rst.

« AI agents MUST NOT add Signed-off-by »: only a human certifies the DCO.

Yes, if a human owns every line.
OpenClaw fastest-growing project · 381k ★

Wrote it down for the agents: VISION.md + AGENTS.md, in the repo.

Every PR: real-behavior proof, a human signs the merge.

The human is still the bottleneck, on purpose.

An agent is only as good as the docs and the rules you give it.

Back to LOTUSim · the scenario we'll walk through

Adding an RC sailboat
that rounds a race buoy.

A real feature, end to end. Non-trivial on purpose:
it touches the whole stack:

  • physics/: a 6-DOF hydro/aero model (sail, keel, rudder),
  • systems/: engine glue for angle-commanded control surfaces,
  • assets/: the boat model and its mesh,
  • worlds/: a buoy-rounding scenario with a closed-loop helmsman,
  • docs/: the spec page and how to run it.
↳

Stated objective

From zero knowledge of the repo,
to a PR ready for review,
in a single work session.

No magic. Just method.

The agent wires the structure: the model skeleton, the engine glue, the scenario.
The hydro/aero model stays the naval engineer's, plugged in and validated before merge.
