Where we stand

Contributing to a robotics sim
is a wall.

01

Technical surface

Modern C++, CMake, ROS, Gazebo plugins, SDF/URDF, Xdyn. Every brick has its idioms. The learning curve is real.

02

Physical coupling

A sensor isn't just a class: it's a physical model, a ROS message, a Gazebo plugin, and a launch scenario integration.

03

Implicit conventions

Topic naming, plugin structure, C++ style, launchfile format. All the things never written in the README.

→ Many good ideas die between « I want to contribute » and « my PR is ready ».

Why now

AI agents crossed the useful threshold.

Not for demos. For production code.

Three things shifted late 2025:

  • Models good at tool calling. With Opus 4.5, GPT-5.2, multi-step tool chains finally stay on track.
  • Long context windows. A full codebase + docs + conventions fits in one shot, no more lossy summaries.
  • Sustained autonomy. What holds a task together over hours isn't a bigger prompt. It's the agentic loop: map → build → run → test → review, repeated until it's green.

→ Which raises the real question: how do we handle agent-assisted contributions, responsibly? Two communities already answered.

Industry signal · the Linux kernel

The most conservative community
took the time to answer.

After months of debate, the Linux kernel published its first official policy on AI-assisted contributions, a document addressed to the agents and to the people who run them.

  • A dedicated file, Documentation/process/coding-assistants.rst, written for AI tools, not just humans.
  • No ban, no hype. AI is « just a tool ».
  • « AI agents MUST NOT add Signed-off-by »: only a human can certify the DCO.
  • The human reviews everything, signs, and owns the licence and the bugs.
Their answer: yes, under one condition. The human who signs answers for every line.
# linux/Documentation/process/coding-assistants.rst
Assisted-by: AGENT_NAME:MODEL_VERSION [TOOL1] [TOOL2]

# verbatim example from the doc
Assisted-by: Claude:claude-3-opus coccinelle sparse

# the line that does NOT move
→ AI agents MUST NOT add Signed-off-by
→ only a human certifies the DCO
→ the human reviews all AI code, and owns it

Industry signal · built on agents

And the fastest-growing project
wrote it all down.

OpenClaw (Peter Steinberger): built agent-first, end to end, and now the fastest-growing open-source project in GitHub history. It runs on what they wrote down for the agents:

  • VISION.md: what to build, and what to refuse.
  • AGENTS.md: how to map, build and test, right in the repo.
  • Every PR needs real-behavior proof; 28+ humans sign the merge.
  • Steinberger's conclusion today: the human is still the bottleneck, on purpose.

To get there, Steinberger himself runs ~100 agents in parallel (≈$1.3M of tokens in one month, OpenAI-funded; he was since hired by OpenAI). The lesson isn't the scale, it's the discipline: an agent is only as good as the docs and rules you give it.

↻The method · from clone to PR in one session

The loop, on the sonar.

  • Mapthe agent reads the repo, finds the closest analog (a depth-camera plugin), answers with file:line, in minutes, not days.
  • Planit proposes 2–3 strategies with trade-offs. I choose.
  • Buildit runs colcon + the sim, reads the failure, fixes, then closes the loop itself.
  • Docit writes the docs page + a notebook example while the « why » is fresh.
  • Shiplabelled issue → fork → PR, Assisted-by: + I sign.

Honest limits: the price of velocity

What I'm not selling you.

!

Govern what the agent touches

Open-source LOTUSim is public, so sharing it with an agent is fine. The real risk: without clear rules, an agent pulls in something that shouldn't land in a public repo. Match the guard to the data, and write the rules down.

!

Hallucinations

In C++/ROS/Gazebo, the agent sometimes invents Gazebo APIs that no longer exist, or confuses versions. Build + tests = mandatory safety net.

×

Supervision is not optional

No « dark factory » (Steinberger). An agent that can write and commit needs to be supervised like a junior dev, not as a metaphor.

×

Not a substitute

AI is « just a tool » (Torvalds). Without a real foundation in C++/ROS/physics, the agent helps you hit the wall faster.

What this asks of the project

An agent is only as good as
the docs it can read.

LOTUSim today
  • README.md: one paragraph.
  • CONTRIBUTING.md: written for humans.
  • Docs live in a wiki, not in the repo.
  • Testing guide: « available soon ».
  • Nothing addressed to the agents.
Agent-ready: the homework
  • AGENTS.md: how to map, build, test, plus the conventions.
  • VISION.md in the repo: the roadmap, and what we won't merge.
  • Docs-as-code: same repo, same PR, same review.
  • A test suite + local CI, so the agent can close the loop itself.
  • An AI-contribution policy (Assisted-by, the human signs) with review guardrails.

→ The wall from the start, those implicit conventions, is exactly what these files write down. Lower it for humans, and you lower it for agents too.

Closing
