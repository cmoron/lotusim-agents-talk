Where we stand

Contributing to a robotics sim
is a wall.

01

Technical surface

Modern C++, CMake, ROS, Gazebo plugins, SDF/URDF, Xdyn. Every brick has its idioms. The learning curve is real.

02

Physical coupling

A sensor isn't just a class: it's a physical model, a ROS message, a Gazebo plugin, and a launch scenario integration.

03

Implicit conventions

Topic naming, plugin structure, C++ style, launchfile format. All the things never written in the README.

Many good ideas die between « I want to contribute » and « my PR is ready ».

Why now

AI agents crossed the useful threshold.

Not for demos. For production code.

Three things shifted late 2025:

  • Models good at tool calling. Opus 4.5, GPT-5.2: multi-step tool chains stay on track.
  • Long context windows. A whole codebase + docs + conventions in one shot, no lossy summaries.
  • Sustained autonomy. Not a bigger prompt: the agentic loop, map → build → run → test → review, until green.

Adding an RC sailboat
that rounds a race buoy.

A real feature, end to end. Non-trivial on purpose:
it touches the whole stack:

  • physics/: a 6-DOF hydro/aero model (sail, keel, rudder),
  • systems/: engine glue for angle-commanded control surfaces,
  • assets/: the boat model and its mesh,
  • worlds/: a buoy-rounding scenario with a closed-loop helmsman,
  • docs/: the spec page and how to run it.

Honest limits: the price of velocity

What I'm not selling you.

!

Govern what the agent touches

Open-source LOTUSim is public, so sharing it with an agent is fine. The real risk: without clear rules, an agent pulls in something that shouldn't land in a public repo. Match the guard to the data, and write the rules down.

!

Hallucinations

In C++/ROS/Gazebo, the agent sometimes invents Gazebo APIs that no longer exist, or confuses versions. Build + tests = mandatory safety net.

×

Supervision is not optional

No « dark factory » (Steinberger). An agent that can write and commit needs to be supervised like a junior dev, not as a metaphor.

×

Software wall ≠ domain wall

AI drops the software wall in hours: install, launch, first feature, first bugfix, even a model that runs. The domain wall stays: making it true to the real vessel (the hydro/aero coefficients) needs naval expertise. Without it, the agent only gets you to that wall faster.

What this asks of the project

An agent is only as good as
the docs it can read.

LOTUSim today
  • README.md: one paragraph.
  • CONTRIBUTING.md: written for humans.
  • Docs in a wiki, not the repo.
  • Testing guide: « available soon ».
  • Nothing addressed to the agents.
Agent-ready: the homework
  • AGENTS.md: map, build, test, conventions.
  • VISION.md in the repo: roadmap, and what we won't merge.
  • Docs-as-code: same repo, same PR, same review.
  • A test suite + local CI: the agent closes the loop itself.
  • SECURITY.md: report a vulnerability, before contributions scale.
  • An AI-contribution policy: Assisted-by, the human signs, with guardrails.

The wall from the start, those implicit conventions, is what these files write down. Lower it for humans, you lower it for agents too.
