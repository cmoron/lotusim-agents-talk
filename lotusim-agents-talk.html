Where we stand

Contributing to a robotics sim
is a wall.

01

Technical surface

Modern C++, CMake, ROS, Gazebo plugins, SDF/URDF, Xdyn. Every brick has its idioms. The learning curve is real.

02

Physical coupling

A sensor isn't just a class: it's a physical model, a ROS message, a Gazebo plugin, and a launch scenario integration.

03

Implicit conventions

Topic naming, plugin structure, C++ style, launchfile format. All the things never written in the README.

→ Many good ideas die between « I want to contribute » and « my PR is ready ».

Why now

Agents crossed the useful threshold.

— not for demos. For production code.

Three things shifted recently:

  • Long, structured context. An entire codebase plus docs plus conventions fits in the agent's window.
  • CLI and orchestration. Agents act: they read, write, build, run tests, open PRs.
  • Open protocols (MCP). Agents plug into your tools — issues, docs, build — not the other way around.
# what wasn't true 18 months ago
$ claude "explain the Gazebo plugin → ROS topic pipeline in systems/"

→ two strategies, explicit trade-offs

$ claude "implement option B + tests + doc"
→ readable first draft, ready to challenge
Industry signal · legitimacy

The Linux kernel made the call.

After months of heated debate, the kernel published its first official policy on AI-assisted contributions.

  • A dedicated document in Documentation/process/coding-assistants.rst.
  • AI is « just a tool » — Torvalds' position, codified in the docs.
  • No ban. No evangelism. Full human responsibility.
  • Signed-off-by stays human (DCO). The submitter owns the code, licence, and bugs.
The documentation is for good actors. — L. Torvalds · LKML, jan. 2026

Industry signal · practice

What the pioneers learned.

①

Close the loop

The agent must compile, run, and test its own work. Without a closed feedback loop, you're not doing serious work.

②

Prompt > pull request

Steinberger reads the prompt more than the diff. The quality of the ask predicts the quality of the result better than the code does.

③

Architecture > code review

The human debate moves up a level: we discuss decisions, not lines. Line-by-line review can be delegated.

④

Transparency

Assisted-by tag, versioned prompts, clear attribution. No shame, no hiding. Linux set the standard.

⑤

The human signs

DCO is human-only. No blind auto-merge (« dark factory »). Someone is on the hook for what ships.

⑥

Learn the agent

Like an instrument. First session frustrating? Normal. You learn its strengths and weak spots the way you'd learn a new teammate.

→ None of these is tied to a specific tool or vendor. Portable.

Stage 01 · MAP

Understanding the codebase
in minutes, not days.

What the agent does, concretely:

  • walks the tree, reads CMakeLists, follows #includes,
  • identifies where Gazebo plugins live and their lifecycle,
  • answers « where is the AUV → ROS topic wiring defined? » with files and lines,
  • produces a digest the next stages can reuse.

Typical tools: Claude Code, local RAG on Gazebo/ROS docs, grep/clangd.

// abbreviated session
› how are Gazebo sensor plugins wired to ROS in this repo?
# systems/sensors/<type>/ : plugin + ROS publisher
# pattern: gz::sim::System + ros_gz_bridge config

› show the closest existing analog to a sonar
# systems/sensors/depth_camera/ — same lifecycle,
# different physics + different msg type

› summarise contribution conventions (CONTRIBUTING.md)
→ issue → label → fork → PR → review (maintainers or committee)
Stage 02 · PLAN · this is where taste lives

Where taste
shows up most.

The architect agent doesn't write code. It proposes.

  • 2 to 3 distinct integration strategies,
  • impact on existing modules,
  • risks, potential debt, alternatives,
  • a step-by-step execution plan, calibrated for the PR.
Taste and system design remain the ultimate moats. — P. Steinberger · State of the Claw, 2026

My human edge: choosing. Quickly. Wisely. That's the part that doesn't transfer to the agent.

Expected output
Option A — « ideal » analytical range-bearing sensor.
+ simple, fast · − acoustically thin

Option B — Gazebo ray-casting + tunable attenuation.
+ realistic, extensible · − more code, more tests

Option C — wrap a third-party acoustic plugin.
+ state of the art · − external dep, licence check
↻Stage 03 · BUILD · close the loop

First draft of code,
in one flow.

What really changes is not typing speed. It's the cycle:

  • you describe intent and constraints,
  • the agent proposes plugin C++ + CMake + message + tests,
  • you run colcon build and the sim locally,
  • you steer by exception, not by dictation.

Local CI > remote CI — the agent sees the failure in 12 seconds, not 10 minutes.

Stage 04 · DOC

Docs while you still know
why you did it.

The classic trap: documenting later = never.

  • the agent writes in the project's format (Markdown, docs/ structure),
  • it picks up the decisions from the PLAN stage,
  • it generates a Jupyter example consistent with examples/jupyter-python/,
  • you read, refine, sign off.

→ Docs become a deliverable of the same session, not debt.

Why it works now

Docs-as-code fits the agent flow perfectly: same repo, same PR, same review. The agent sees the code, the tests, the launch scenario. It has everything it needs to write what you would have written yourself if you'd had the time.

Honest limits — the price of velocity

What I'm not selling you.

!

Hallucinations

In C++/ROS/Gazebo, the agent sometimes invents Gazebo APIs that no longer exist, or confuses versions. Build + tests = mandatory safety net.

!

Attack surface

OpenClaw: 1,142 advisories in 5 months, 2× the kernel rate. Velocity creates perimeter. Bake it into review.

!

Silent debt

Code that compiles and passes tests is not clean code. Without an architecture that fits in a human head, debt piles up fast.

×

Security & confidentiality

Whatever leaves the workstation must be allowed to leave. Self-hosted models, local RAG, context separation: non-negotiable depending on the environment.

×

Supervision is not optional

No « dark factory » (Steinberger). An agent that can write and commit needs to be supervised like a junior dev — not as a metaphor.

×

Not a substitute

AI is « just a tool » (Torvalds). Without a real foundation in C++/ROS/physics, the agent helps you hit the wall faster.

What this changes for LOTUSim

The entry barrier
drops an order of magnitude.

  • For a contributor: from « weeks before my first contribution » to « a useful PR in the first session ».
  • For the project: more, better-prepared PRs → less friction in review → shorter cycles.
  • For the community: profiles who wouldn't have crossed the technical wall — researchers, integrators, partners.
  • For the governance committee: less « where do I start? », more « here's a documented proposal, what do you think? ».
The moment

LOTUSim is publishing its first roadmap in 2026, releases are biannual, the governance committee will open to major contributors.

And the agentic tooling to contribute cleanly is mature today: Linux wrote the contract, OpenClaw proved the scale.
